## Device: reboot into App setup after a network test (upstream bug, B-018)

Firmware: `feat/idle-behavior` at `5ef1a3c` (idle tuning, Melbourne timezone, `SC_DISABLE_REMOTE_OTA`).

- Settings > System: timezone changed to "Melbourne (AEST/AEDT)"; kept after the reboot
  (`load timezone from nvs: AEST-10AEDT,M10.1.0,M4.1.0/3`). ✔
- Settings > Network test: Wi-Fi started and connected, Xiaozhi `available`, M5Stack `reachable`.
- About 7 min later AI Agent was opened: `WifiManager: Already initialized`, `Station already active`, then after 60 s
  `WiFi connection timeout, entering config mode` → `WiFi setup required; opening StackChan App setup` → software
  reset (`RTC_SW_CPU_RST`, no panic; free internal SRAM ≈ 74 KB at that point).
- After the reboot the launcher logged `resume App setup after network/binding failure` and showed the APP SETUP page
  with BLE provisioning, which looked like an unbound device.
- Cause (source review): the network test starts Wi-Fi through `WifiManager` directly and leaves the station connected.
  `WifiBoard::TryWifiConnect()` arms its 60 s timer and waits for a `Connected` event that had already happened; the
  board maps config mode to `requestAppSetup()` (one-shot NVS flag + reboot). None of these files are changed by the
  fork, so official 1.6.0 behaves the same.
- Nothing was lost: the xiaozhi binding is server side, `app_config/is_configed` is untouched and the Wi-Fi credentials
  are kept. The maintainer pressed RST: normal launcher, AI Agent works again. ✔
- Recorded as B-018; no code change for now (maintainer decision). Workaround: reboot after a network test.

## Reports after a night of use; REQ-004 (branch `fix/standby-power`)

Maintainer reports: screen too dark while sleeping; no standby on USB; a restart after a long idle that looked like a
Wi-Fi crash.

Investigation (5 parallel source/schematic studies, 4 of them checked by an adversarial second review):
- Restart = the AI Agent Home button (swipe up + tap Home, confirmed by the maintainer). Leaving AI Agent always
  restarts; the Wi-Fi/TLS errors are `esp_restart()` stopping Wi-Fi. No panic. Side finding: a tap on the dim sleeping
  face starts a conversation (the director ignores screen touches), and a bottom-edge swipe can toggle it.
- Sleep backlight 5 is already the dimmest visible step (AXP2101 DLDO1, 9 steps of 100 mV; 1–12 = 2.5 V).
- On USB the upstream power-save timer is already off unless the PMIC reports discharging. The servos always run from
  the cell through the body boost converter (schematics), so "not running from battery" cannot be fully guaranteed;
  the body INA226 (0x41) sees the real cell current. The firmware's "external power" flag never read VBUS.
- Claude Code status robot: USB link over the native USB-Serial/JTAG is feasible (~1 KB internal RAM); MQTT relay
  feasible (~5–8 KB internal RAM, task stack stays internal). HiveMQ Serverless is being retired (2026-12-31).

Decisions: USB keeps the night schedule; lit-room sleep backlight 45; no hold-to-confirm on Home. Claude Code design
answers recorded in [REQ-003](../requirements/REQ-003-claude-code-status.md) (WSL sessions, Python agent, NAS with static
IP, quiet working hours, project + event in the bubble).

Implementation (see [REQ-004](../requirements/REQ-004-standby-power-touch.md)): lit/dark sleep backlight with fade,
screen tap wakes the sleeping face, swipe filter, Home slide guard and "Going home..." before the restart, FT6336
sample check, reset reason log, core dumps to flash, VBUS-based debounced external power with a power log (INA226 cell
current), no power-save on USB, bolt in the status bar, power-save exit restarts the director.

Code review of the diff (4 dimensions, each finding verified) found 6 real problems, all fixed:
- the "Going home..." overlay stayed on top of the launcher when Settings went home without a restart (now owned and
  deleted by the indicator, not clickable, shown only when going home restarts);
- `Backlight::SetBrightness` ignored a second call while a transition to another target was pending, so the power-save
  dim was lost in a dark room (fixed in the xiaozhi fork patch: retarget pending transitions);
- `lv_refr_now()` on the 4 KB stackchan task (now the LVGL task draws the overlay, home follows 300 ms later);
- a click made just before the Home button timed out was dropped; a race between the power-save dim and a wake-up;
  implausible touch samples were turned into a release (now dropped, release only after 5 in a row);
- sleep backlight could light up a screen whose normal brightness is 0.

Build (fresh sdkconfig, ESP-IDF 5.5.4): passes, no warnings from changed files, `stack-chan.bin` 3.60 MB (27 % free).
Core dump reserves a 1.8 KB internal-RAM stack (coredump log strings disabled). **Not yet flashed.**
